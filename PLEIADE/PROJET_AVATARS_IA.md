# Projet — Avatars animés par IA sur le réseau social de PLÉIADE

> Projet piloté par l'agent **PLEIADE** (décision utilisateur du 2026-10-10). Ouvert à partir d'un cadrage rédigé dans une discussion sur l'app Claude (« simulation de réseau social avec avatars IA, Mastodon + Ollama »), puis **confronté à ce qui existe déjà** dans PLÉIADE et MINERVE.
> **Statut : cadrage — rien n'est construit.** Première étape retenue par l'utilisateur : un prototype à **un seul avatar**, hors réseau.

---

## 1. Ce que veut l'utilisateur (repris du cadrage)

Un moteur, piloté depuis une console, qui fait **réagir des avatars fictifs** quand de vrais participants publient (réponses, J'aime, abonnements), pour que le réseau paraisse vivant ; plus tard, un **fil « Pour toi »** algorithmique pour les participants.

Décisions déjà prises dans le cadrage, toujours valables :
1. **L'IA n'écrit que les textes.** Choisir qui voit quoi et qui réagit = **code classique** (filtres, score pondéré, tirage) ; les embeddings ne servent qu'à mesurer une affinité thématique.
2. **Validation humaine au départ** : le moteur propose, l'animation approuve / modifie / rejette ; l'automatique vient après.
3. **Débit** : au plus **1 texte généré par minute**, un appel à la fois ; J'aime et abonnements sans IA, donc bien plus nombreux.
4. **Ollama hors du serveur** (le serveur n'a pas de GPU) : Mac M3 Max 36 Go en machine principale, Legion RTX 5070 Ti en second nœud ; modèles à comparer : `gemma3:27b`, `mistral-small:24b`, `qwen3:32b` (repli 12-14b) ; embeddings `bge-m3`.
5. **Prompt en 4 couches** : fiche de l'avatar (avec 5 à 10 exemples de messages), contexte global du réseau, mémoire de l'avatar, contexte immédiat (le post et son fil).
6. **Ne pas réutiliser tels quels** les dépôts d'algorithmes de X/Twitter (s'en inspirer seulement, licences à vérifier).

## 2. Ce qui change parce que le réseau n'est PLUS Mastodon

Le cadrage a été écrit pour une instance **Mastodon**. Le réseau de l'exercice est **`app-social`** (« Social »), notre propre application de zone PLÉIADE (dépôt `cecpc-pleiade/app-social`, ex-`mastorion`). Conséquences :

| Dans le cadrage (Mastodon) | Dans PLÉIADE (réalité) |
|---|---|
| Mastodon.py, webhook `status.created`, `tootctl` | **API de service de Social** (`/api/service/*`, clé de zone) : `publish` (post, réponse, citation, lieu, sondage, origine), `chat` (message privé), J'aime générés (`likes_identity_ids`). Pas de webhook aujourd'hui : **à ajouter** (ou lecture périodique du fil). |
| « Un avatar = un compte Mastodon avec son jeton » | **Un avatar = une identité eho** (UUID). Aucun jeton par avatar : la Console publie « au nom de » avec la **clé de service**, Social vérifie. Les 4 000 jetons chiffrés du cadrage **ne sont pas nécessaires**. |
| Créer 4 000 comptes par script | Les avatars **existent déjà dans eho** (modèles d'exercice, groupes, camps) ; eho fait foi pour l'identité. |
| Boosts générés | ⛔ **Repost simple désactivé** sur Social depuis le 2026-10-09 (décision utilisateur « réalisme et égalité ») : on relaie par **citation**, donc un texte écrit par l'IA. |
| Forker Elk / Phanpy pour un onglet « Pour toi » | Social est **à nous** : l'onglet se code **directement** dans `app-social` (pas de fork, pas d'OAuth à monter). |
| Console d'administration à construire (FastAPI) | La **Console d'animation** (`app-admin`) existe : scénarios, éléments en **brouillon** → **programmés**, contrôle de cellule, origine, journal. C'est la **file de validation** naturelle. |
| Fédération à couper | Social n'est pas fédéré (réseau fermé de zone). |
| Tailscale pour joindre Ollama | PLÉIADE a déjà son **VPN de zone** (Pritunl, `pleiade-infra`) ; le chemin serveur → Ollama est **à décider avec CYBERSECU** (jamais exposé sur Internet). |

## 3. Ce qui existe déjà et peut servir (ne pas le refaire)

- **Fiche avatar** : eho porte déjà les champs d'un profil — âge, genre, pays, origine, religion, situation, **caractère**, **langage**, activité, observations, qualifications, **aime / déteste**, `bio` (fiche interne) et `bioPublique`, groupes (camp, cellule), certification. Il manque : **exemples de messages**, **plages d'activité**, **taux d'action** (bavard / silencieux) → à ajouter (dans eho, propriétaire de l'identité, ou dans le moteur — à trancher).
- **Camp et doctrine d'un personnage** : propriétaires uniques déjà fixés — camp = registre MASTAURIGE / entités du vault ; doctrine narrative = l'**Analyste du pays** (Mercure, Arnland, Bothnia). Le moteur **cite** ces sources, il ne les recopie jamais (règle anti-divergence de `CLAUDE.md` : un camp faux produit l'effet ILI **inverse**).
- **Contexte global du réseau** (couche 2) : **MELMIL** (incidents, storylines, jours D+), les **lignes opératoires GLM26** et la doctrine d'**EXPERT_INFLUENCE**, les **countrybooks** des Analystes, les scénarios déjà programmés dans la Console. La couche « manuelle » du cadrage existe donc en grande partie.
- **Sélection des réacteurs** : `choisirComptes` (Social) tire déjà des avatars **au hasard dans le camp de l'auteur** pour les J'aime générés — point de départ du futur score (affinité, relation, fraîcheur, aléa).
- **Affinité thématique / embeddings** : le module **Sentinel** est toujours dans `app-social` (`sentinel-api`, `sentinel-ui`, `sentinel-worker`) : embeddings **pgvector**, topics BERTopic, Ollama — spécification `app-social/docs/sentinel-spec.md`. À réutiliser plutôt qu'un nouvel index.
- **Traçabilité** : l'**origine des publications** (2026-10-09) enregistre qui a produit chaque post (joueur, animation, scénario) — ajouter un type **« IA »** pour que l'animation voie ce qui vient du moteur.
- **Kit IA de la Console** : prépare déjà des scénarios avec une IA externe (Excel) — version « hors ligne » du même besoin.
- **Expérience Ollama locale** : les agents locaux de MINERVE tournent sur Ollama (qwen2.5-coder, deepseek-r1:14b, mistral-nemo, llama3.1) ; **MINERVE Local** (RAG, en pause) a montré que **`bge-m3` est lent sur le poste Windows** (~2,2 s par embedding) → à remesurer sur le Mac.
- **Mesure** : le **Cockpit** (Reporting, Activité par heure, origine) permettra de voir l'effet du moteur.

## 4. Règles du projet qui s'imposent au moteur

- ⛔ **Jamais de personne réelle** imitée ; avatars fictifs seulement.
- ⛔ **Fiches bio** (`DOC REF\MERCURE\RENS\01_Fiches bio`) : jamais lues ni indexées par Claude ; une IA **locale** peut les indexer dans une **collection séparée** que Claude n'ouvre pas (règle MINERVE Local).
- **Langue du texte = langue de l'avatar** ; « GET » pour la zone fictive, jamais « Europe » ; numéros fictifs ; cohérence géographique (localités « H… », phase D+).
- **Camp juste** (registre MASTAURIGE), **cellule** respectée (même contrôle que la Console).
- **Validation humaine** tant que la qualité n'est pas prouvée ; **journal** de tout ce qui est publié ; sujets interdits paramétrables.
- **Cadre de l'exercice** : les participants savent qu'ils sont dans un environnement simulé (bandeau « Exercice ») ; l'origine « IA » reste visible de l'animation seulement.
- **Plateforme** : 1 app = 1 dépôt dans `cecpc-pleiade` (une future app `app-ia` ou équivalent), Keycloak, découverte de zone, clé de service, **test local Docker avant tout push**, **notes de version**, aucun secret en dur.
